## 1. 背景与目标

### 1.1 业务背景
AIGC 能力（文生图、文生视频、AI 配音等）正以开放平台形式向开发者与企业输出。此类平台的核心后端挑战：

1. **开发者生态**：开发者注册账号、创建应用、获得 AppKey/AppSecret，以签名方式调用开放 API；
2. **计量计费**：能力按「积分」计量，开发者购买订阅套餐（含月度积分额度）或积分包，调用前预扣、失败退款；
3. **异步任务**：AIGC 推理耗时长（数秒到数分钟），必须异步化：提交任务 → 排队执行 → 回调/轮询结果；
4. **开放网关**：认证、防重放、限流、熔断降级，保护后端推理资源；
5. **可靠性**：支付回调可能重复投递、推理可能失败、服务可能宕机，资金账务（积分）不可出错。

### 1.2 产品目标
构建一个**可真实运行、可验收、面向生产标准**的 AIGC 开放平台后端：

- G1：开发者可以从注册 → 创建应用 → 购买积分 → 调用 API 创建 AIGC 任务 → 获得结果回调，全流程无人工干预；
- G2：所有资金敏感操作（支付、积分扣减/退款）在异常与并发下保持**正确且幂等**；
- G3：任一依赖故障（计费服务宕机、推理失败、支付渠道重发通知）不产生脏数据，系统可自愈或快速失败；
- G4：全链路可观测（traceId、指标、健康检查），可压测、可运维。

### 1.3 非目标（本期范围外）
- 真实对接支付渠道（支付宝/Stripe）与真实 AI 推理模型：以「渠道模拟器 + 可配置故障率的模拟推理引擎」替代，接口契约按真实渠道设计，后续可替换实现；
- 控制台 Web 前端、管理后台、多租户企业版（见路线图 docs/08）；
- 跨机房多活、单元化部署。

## 2. 术语表

| 术语 | 定义 |
| --- | --- |
| 开发者用户（User） | 在平台注册的账号主体 |
| 应用（App） | 开发者创建的调用单元，拥有 AppKey/AppSecret 与回调地址 |
| 积分（Credit） | 平台计量货币。1 次任务消耗 N 积分（按任务类型定价） |
| 预扣（Hold） | 任务提交时冻结积分，成功后结算（Settle），失败/超时后退还（Refund） |
| 订阅（Subscription） | 周期性套餐，含每月积分额度 |
| 任务（Task） | 一次 AIGC 异步调用，具有状态机生命周期 |
| Outbox | 本地消息表，保证「业务落库」与「消息投递」最终一致 |
| 幂等键（Idempotency-Key） | 客户端为可重试请求提供的唯一键，服务端保证同键同果 |

## 3. 角色与用户故事

**R1 开发者（主角色）**
- US-01：注册账号（邮箱+密码），登录获取访问令牌，可刷新、可登出；
- US-02：创建应用，获得 AppKey/AppSecret（Secret 仅创建时明文可见一次），可重置；
- US-03：查看/购买套餐与积分包，创建订单，模拟支付后权益自动到账；
- US-04：以 AppKey 签名方式提交 AIGC 任务（文生图/文生视频/文生语音），系统校验签名、防重放、检查积分并预扣；
- US-05：任务异步执行完毕后，平台向应用配置的 callback_url 发起 Webhook 通知（失败自动重试）；也可轮询任务详情；
- US-06：任务失败或超时自动退还预扣积分，可在流水（ledger）中追溯每一笔变动；
- US-07：用同一个 Idempotency-Key 重试提交，不会产生重复任务、不会重复扣积分。

**R2 平台运维（次角色）**
- US-08：通过 /actuator 健康检查与 Prometheus 指标监控各服务；
- US-09：通过统一错误码与 traceId 定位跨服务问题；
- US-10：限流/熔断配置可调，无需改代码。

## 4. 功能需求（FR）

### FR-01 账号（tg-account）
| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-011 | 邮箱+密码注册，密码 BCrypt 存储；邮箱唯一约束 | P0 |
| FR-012 | 登录签发 AccessToken(JWT, 30min) + RefreshToken(7d, 哈希落库、轮换、可撤销) | P0 |
| FR-013 | 刷新令牌：旧 RefreshToken 一次性作废（轮换），被盗检测（已用 token 再次使用 → 撤销整个家族） | P0 |
| FR-014 | 登出：RefreshToken 撤销；AccessToken 走短时效（网关侧无黑名单，见 05 文档权衡说明） | P1 |

## 5. 非功能需求（NFR）

| 编号 | 类别 | 指标 |
| --- | --- | --- |
| NFR-01 | 性能 | 单机 local 模式：任务提交接口 P99 < 300ms（不含推理）；网关限流 1000+ QPS 能力（令牌桶内存路径） |
| NFR-02 | 一致性 | 支付回调重复投递 N 次 → 恰好发货一次；积分预扣与任务状态在任意时点对账不平 → 有流水可修复 |
| NFR-03 | 可用性 | 任一业务服务停止：网关 503 快速失败（<1s，熔断后）；task/billing 重启后 Outbox/未结算任务自动续处理 |
| NFR-04 | 安全 | 密码 BCrypt；Secret AES-GCM 加密存储、仅显示一次；HMAC 签名防篡改防重放；常量时间比较 |
| NFR-05 | 可测试性 | 单测覆盖核心域逻辑（状态机、幂等、账务）；`mvn verify` 一键全绿，不依赖外部环境 |
| NFR-06 | 可运维性 | 一条命令拉起全栈（local 或 docker）；冒烟脚本输出验收结论 |

## 6. 关键验收场景（摘要，完整手册见 docs/06）

1. **全流程**：注册→建应用→下单→支付回调→积分到账→签名提交任务→异步成功→Webhook 收到通知→查询结果；
2. **幂等**：同一支付回调重放 3 次，积分只加一次；同 Idempotency-Key 提交 3 次任务，只产生 1 个任务、一次预扣；
3. **容错**：把模拟推理失败率设为 100% → 任务重试后最终失败且积分自动全额退回；停掉 billing 服务 → 提交任务被熔断快速失败，恢复后自动闭合；
4. **并发**：两个并发请求竞争同一份积分余额，账务零丢失（乐观锁重试）；
5. **超时**：构造超 TTL 任务 → 自动 TIMEOUT + 退款。
