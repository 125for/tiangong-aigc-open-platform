# 天工 TianGong · 容错与高可用设计

文档版本：v1.0（2026-10-18）。本文档定义每一类故障场景与对应机制，是本项目的核心价值所在，也是验收「抗错误能力」的依据。

## 0. 设计原则

1. **失败是常态**：网络抖动、进程崩溃、重复投递、并发冲突都视为正常输入，而非异常分支；
2. **资金操作只准确或快速失败，绝不降级伪造**（预扣失败就不接单，绝不"先跑后退"裸奔）；
3. **幂等是第一道防线**：一切可重试操作先设计幂等键，再谈重试；
4. **每个后台自愈任务必须可观测、有上限**：重试有次数、退避有上限、死信有人工出口。

## 2. 关键机制详解

### 2.1 幂等的三层实现
```
L1 API 层：Idempotency-Key 头 → idempotency_keys 表（唯一约束抢占 PROCESSING 位）
           命中 DONE → 直接回放 response_json（同键同果）
           命中 PROCESSING → 409 提示稍后重试（避免并发双跑）
L2 业务层：账务迁移唯一约束 (biz_type, biz_no, change_type)，支付单 payment_no 唯一
L3 状态机：任务/订单状态迁移带 version 乐观锁，非法迁移直接拒绝
```
> 为什么不只用 Redis `SETNX`：Redis 数据丢失（重启/淘汰）会造成幂等失效，资金场景以 DB 为准绳；Redis 仅用于 nonce/限流这类可容忍极小概率失效的场景。

### 2.2 预扣—结算—退款（跨服务最终一致）
```
提交任务(task) ──hold(bizNo=taskNo)──▶ billing: held+=N, ledger(HOLD)
   │ 成功 → task 落库 PENDING
   │ 失败(余额不足/熔断) → 拒绝提交，无副作用
执行成功 ────settle(bizNo)──▶ billing: held-=N, balance-=N, ledger(SETTLE)
执行最终失败/超时/取消 ─refund(bizNo)──▶ billing: held-=N, ledger(REFUND)
```
- 三个接口均以 `bizNo` 幂等：task 侧重试安全；
- 定时巡检（M2 里程碑）：PENDING 终态任务若 hold 未终结超过阈值 → 自动补偿 refund 并告警（当前版本通过 `/internal/v1/credits/holds/{bizNo}` 可人工核查）；
- settle/refund 只对存在未终结 HOLD 的 bizNo 有效，否则返回幂等成功（防重放后重复入账）。

### 2.3 Outbox 本地消息表（替代事务消息）
```
[Tx] task INSERT + outbox INSERT(PENDING)      ← 同一本地事务，原子
[Relay 每 2s] SELECT ... WHERE status=PENDING AND next_attempt_at<=now LIMIT n
      → dispatch(MQ/进程内) 成功 → SENT；失败 → attempts+1, 指数退避; 超 10 次 → DEAD(人工)
消费端（Worker）按 taskNo 幂等（状态机拒绝重复 RUNNING）
```
为什么不用"先落库再发 MQ"：发送成功前宕机 = 消息丢失；反之先发后落库 = 有消息无数据。Outbox 保证"落库即可靠送达"。

### 2.4 熔断与降级（Resilience4j）
| 依赖 | 熔断参数 | 半开探测 | 降级行为 |
| --- | --- | --- | --- |
| task→billing(hold) | 滑动窗口 20 次，失败率 ≥50% 开闸，等待 20s | 放行 3 个探测请求 | 快速失败 D0101（不接单） |
| task→billing(settle/refund) | 同上 | 同上 | 不降级：改为投递到 outbox 延迟重试（资金必达） |
| billing→account(校验) | 同上 | 同上 | 查询类：拒绝下单（低频，可接受） |

> 面试要点：**写路径降级 ≠ 返回假成功**。settle/refund 熔断时不丢——转入异步补偿队列，这是"快速失败 + 最终一致"的组合拳。

### 2.5 限流算法（网关）
- 令牌桶：容量 = rate（允许瞬时突发），固定速率补充；
- 维度：客户端 IP（防扫描）与 AppKey（防单应用刷量，应用级配额可由 account 服务下发）；
- Redis Lua 原子实现（docker 分布式）；local 用 ConcurrentHashMap+ 延迟补充（单机语义一致）；
- 响应：`429` + `Retry-After` + 错误体 `A0301`。

### 2.6 超时预算（Timeout Budget）
```
网关→服务 connect 1s / read 5s
task→billing(Feign) connect 1s / read 3s
Webhook 出站 connect 2s / read 5s
任务业务 TTL：默认 120s（PENDING+RUNNING 总预算），到点 TIMEOUT
```
原则：上游超时 > 下游最长真实耗时，避免上游放弃后下游仍在写（配合幂等兜底）。

### 2.7 优雅停机与重启自愈
- `server.shutdown=graceful` + Spring Lifecycle：停机时停止接新请求，在制品任务靠超时扫描兜底；
- 重启后：Outbox 中继继续投递未 SENT 消息；RUNNING 超时任务由扫描器终结并退款——**任何崩溃后无人工介入即恢复一致**。

## 3. 验证方式
每个机制对应 docs/06 验收手册中的可执行用例（如"停 billing → 提交任务 → 观察熔断与恢复"）。模拟推理引擎的失败率/耗时、Webhook 目标、任务 TTL 均可通过配置注入，**故障可一键注入、可观察、可恢复**。
